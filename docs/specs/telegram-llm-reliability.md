# Telegram LLM Reliability and Replies v2.4

## 목적

- 2026-10-13~15 실사용에서 나온 문제 중 v2.3(`docs/specs/telegram-llm-corrections.md`)에서 떼어 낸 나머지를 고친다.
  사진 여러 장, 사진 해석 실패 문구, 사진 대화 기억, bot이 멈추는 문제, 메뉴 제안 유효 시간, 짧은 `/ok` 답장, 동기화 안내,
  콘솔 오류 문구다.
- 근거: `docs/specs/telegram-llm-corrections.md`의 "사용 중 발견한 추가 문제" 6, 7, 8, 10, 13, 15, 16, 18. 설계는 v2.3 계획의
  추가 설계(addendum A1~A3, A5, A8, A10, A11, A13)에 이미 있고, 사용자가 2026-10-16에 추천대로 승인했다(15번: 둘로 나눔).
- `docs/goals.md` 3절 "채팅으로 묻기"를 매일 믿고 쓸 수 있게 한다.

## 범위 / Non-goals

- 범위:
  1. **사진 여러 장(앨범)**: 같은 `media_group_id`의 사진을 잠깐 모아(2초씩, 최대 6초, 최대 4장) 한 번에 해석한다. 캡션은
     앨범 전체에 쓴다. 상한을 넘거나 받지 못한 사진은 "사진 N장 중 M장만 읽었습니다"로 알린다.
  2. **사진 해석 실패 문구**: 캡션에 먹었다는 말("먹었", "먹음", "먹은", "드셨", "ate")이 있고 메뉴 말("메뉴", "menu")이 없을
     때만 값 없는 일반식 기록을 제안한다. 아니면 "사진에 '메뉴' 또는 '먹음'이라고 적어 다시 보내 주세요"라고 하고 아무것도
     쓰지 않는다.
  3. **사진을 대화 기억에**: 기억에 "[사진 N장] 캡션 → 해석 결과 요약"을 남긴다. 코치는 이 기억이 있으면 "사진이 없다"고
     답하지 않는다.
  4. **bot이 멈추지 않게**: Telegram 어댑터가 예상 못 한 예외도 재시도 가능한 오류로 바꾸고, 메시지 처리 중 예상 못 한 오류는
     기록하고 다음 메시지로 넘어간다(연속 5번이면 멈춤). 상태 파일 저장(`os.replace`)이 Windows에서 잠깐 막히면 몇 번
     다시 시도한다. 콘솔 출력이 실패해도 멈추지 않는다.
  5. **실행 기록 파일**: 콘솔 줄을 `telegram\run-YYYY-MM.log`에도 남긴다(시작, 멈춤 이유, 30분마다 "alive", Windows 창 닫힘
     이벤트). 메시지 원문과 token은 넣지 않는다.
  6. **메뉴 제안 유효 시간**: 메뉴 캡처·메뉴 제안은 4시간 유효하다. 식사 기록·수정 제안은 60분 그대로다.
  7. **짧은 한국어 `/ok` 답장**: 기록·수정·void 뒤 CLI 영어 출력 대신 짧은 요약(기록한 식사와 item, 이 끼니 범위, 취소·전체
     보기 명령, 누적)을 보낸다. 요약은 저장 뒤 그 식사를 다시 읽어 만든다. 읽기에 실패하면 CLI 출력을 그대로 보낸다.
  8. **동기화 안내**: "동기화 해줘" 같은 요청은 누를 수 있는 `/daily`, `/refresh`를 안내한다. 자동으로 실행하지 않는다.
     운동 질문에서 동기화가 안 된 것으로 보이면 `/daily`를 한 문장으로 안내한다.
  9. **콘솔 오류 문구**: 네트워크 오류를 `WinError 10054 connection reset by remote host`처럼 번호와 짧은 영어 설명으로 쓴다.
     Windows의 한국어 메시지를 escape해 보여 주지 않는다.
- Non-goals:
  - 동기화를 Telegram에서 자동 실행하지 않는다(후속 후보: 확인 뒤 실행).
  - 입력한 명령을 대화 기록에 남기지 않는다(사용자 결정 2026-10-16).
  - CLI 출력은 바꾸지 않는다. 바뀌는 것은 Telegram LLM 답장, 콘솔 오류 문구, 새 실행 기록 파일이다.
  - migration 없음.

## 명령 예시

Telegram(합성 값, 정확한 문구는 설계에서 정한다):

```text
사용자: (메뉴판 사진 2장, 첫 장 캡션 "점심 추천해줘")
bot:   오늘 점심 메뉴예요. … (두 장의 메뉴를 합친 추천 하나)
```

```text
사용자: /ok_c229
bot:   기록했습니다: 아침 2026-10-14-breakfast-1 (10-14)
       1. 일반식 (메모: 깻잎닭갈비 삼각김밥 1개) - 라벨 kcal 185, 단백질 5 g, 탄수화물 37 g
       2. 닭가슴살 (chicken-breast) 1 pack - kcal 120, 단백질 18 g, 탄수화물 2 g, 지방 4 g
       이 끼니: kcal 305, 단백질 23 g, 탄수화물 39 g, 지방 4 g (값 모르는 항목 1개 빠짐)
       취소: /void 2026-10-14-breakfast-1   전체 보기: /show 2026-10-14-breakfast-1
       오늘 누적 (추정 포함): …
```

```text
사용자: 동기화 해줘
bot:   동기화는 /daily 로 합니다. 운동 하나만 다시 받으려면 /refresh 를 쓰세요.
       /daily
       /refresh
```

콘솔:

```text
telegram: network error (WinError 10054 connection reset by remote host); retrying in 5 s
```

## 규칙

- v2.3 계획의 추가 설계(`.git/muscle50-orchestration/plans/telegram-llm-corrections.md`의 A1~A3, A5, A8, A10, A11, A13)와
  사용자 결정(2026-10-16)을 따른다. 설계 단계에서 v2.3 통합 뒤의 코드에 맞춰 다시 확인한다.
- 앨범은 LLM이 켜져 있을 때만 모은다. LLM이 꺼진 bot은 지금과 byte-identical이다(`getUpdates` 호출 수 포함).
- 앨범의 모든 update ID는 처리 전에 기억해 한 번만 처리한다. 허용 목록, 오래된 메시지, 큰 사진 규칙은 사진마다 그대로다.
- 예상 못 한 오류로 넘어간 메시지는 다시 처리하지 않는다. 상태 파일이 손상됐을 때와 token이 거부됐을 때는 지금처럼 멈춘다.
- 실행 기록 파일은 append만 하고 muscle50이 지우지 않는다. 쓰기 실패는 무시한다. 콘솔 규칙(ASCII, 원문·token 없음)을 따른다.
- 짧은 답장의 숫자는 CLI와 같은 반올림, 범위 규칙(모르는 값은 0이 아님)을 따른다. 실패 답장(`오류:`)은 그대로다.

## 인수 조건

- [ ] AC1: 같은 앨범 사진 2장은 사진 2장이 든 LLM 호출 한 번이 되고 캡션이 적용된다. 상한, 다른 앨범, 오래된·큰 사진,
      한 번만 처리를 확인한다. LLM이 꺼져 있으면 동작과 `getUpdates` 호출 수가 지금과 같다.
- [ ] AC2: 먹었다는 캡션이 있으면 값 없는 일반식 제안, 없거나 모호하면 새 안내 문구이고 아무것도 쓰지 않는다.
- [ ] AC3: 사진 뒤 기억 파일과 다음 호출의 프롬프트, `/memory`에 "[사진 N장] … → …"가 있다. 글 대화의 기억은 그대로다.
- [ ] AC4: 어댑터는 `TelegramUnavailableError`만 낸다(예상 못 한 예외 포함, token 없는 ASCII 문구). 메시지 처리 중 예상 못 한
      오류는 기록하고 계속하며 연속 5번이면 exit 1로 멈춘다. `os.replace`가 잠깐 실패하면 다시 시도해 저장된다. 로그 출력
      실패로 멈추지 않는다.
- [ ] AC5: 실행 기록 파일에 시작, 멈춤 이유, alive 줄이 남고, 메시지 원문·token이 없다. 쓰기 실패는 무시된다.
- [ ] AC6: 메뉴 제안은 4시간 동안 `/eat_`로 고를 수 있고, 식사 기록 제안은 60분 그대로다. 만료 문구가 종류마다 맞다.
- [ ] AC7: `/ok`, `/plain`, 여러 끼니, 수정, void 성공 답장이 짧은 한국어 요약이다. 실패 답장과 입력한 `/log` 답장은 그대로다.
      요약을 만들 수 없으면 CLI 출력을 보낸다.
- [ ] AC8: 동기화 요청에는 `/daily`, `/refresh` 안내만 가고 아무것도 실행·저장하지 않는다.
- [ ] AC9: 네트워크 오류 문구가 WinError 번호와 영어 설명이고, 한국어 Windows 메시지가 콘솔에 나오지 않는다.
- [ ] AC10: 기존 CLI 출력과 LLM이 꺼진 bot은 byte-identical이다.
- [ ] AC11: 품질 게이트 4개가 통과한다.

## 한계 / 후속 후보

- 앨범이 2초 넘게 나뉘어 오면 늦게 온 사진은 따로 해석된다.
- Windows 창 닫힘 기록은 최선 노력이다. PC가 꺼지거나 강제 종료되면 마지막 alive 시각으로만 알 수 있다.
- 후속 후보: 확인 뒤 `/daily` 실행, 입력한 명령의 대화 기록.
- 구현자·검증자가 보고한 한계:
  - 앨범의 늦게 온 사진(약 2초 뒤 또는 4장 초과)은 따로 해석된다. 앨범 모으는 동안 같이 가져온 다른 메시지는 Telegram에 미리 확인(ack)되므로,
    그 사이 bot이 강제 종료되거나 Ctrl+C가 오면 그 메시지는 다시 실행되지 않고 사라진다(두 번 실행되지는 않는다).
  - 읽지 못한 사진도 `keep_photos`가 켜져 있으면 전처럼 보관된다(이 기능 이전과 같음). 해석 실패 때 쓰지 않는 것은 DB, 제안, 상태 파일이다.
  - 실행 기록은 콘솔 줄을 그대로 따라 쓰므로, 예상 못 한 오류의 traceback 마지막 줄(`str(exc)`)에 예외 문구가 들어갈 수 있다(AC5와의 긴장은 설계에서
    승인했고 docs에 known issue로 적었다). token은 가려진다. 구체적으로 메시지 원문이 들어가는 경로는 찾지 못했다.
  - `alive` 줄은 루프가 돌 때 확인하므로 긴 LLM 호출 중에는 비어 있을 수 있다. 메모리 파일(`llm_memory_store`)에는 `os.replace` 재시도를 넣지 않았다.
  - 프롬프트로만 지키는 규칙(운동 질문에서 `/daily` 안내)은 모델이 건너뛸 수 있고, `sync_request` 분류는 문장 두 개로만 확인했다.
  - 라벨 판별은 저장된 근거 문구의 `; 라벨`을 읽으므로 근거 형식이 바뀌면 `추정`으로 보인다. 여러 영양소가 모르는 `이 끼니` 줄은 길어질 수 있다.
  - 아직 하지 않은 수동 확인(자동화 불가, 필수 게이트 아님): 실제 Telegram 앨범 두 장, 창을 닫을 때 `console_event` 줄, 30분 뒤 `alive` 줄.
  - 구현 중 사고: v2.4 테스트 하나가 실제 홈에 `telegram\run-2026-10.log`를 쓰고 세션 출력에 bot token이 찍혔다. `tests/conftest.py`의 자동 격리 fixture로
    고쳤다(운영 데이터 변경 없음). 이 파일을 지울지와 **token 교체**는 사용자가 정할 일로 남아 있다.
