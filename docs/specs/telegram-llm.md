# Telegram Free Text, Photo and Coach v2

## 목적

- Telegram에서 명령어 대신 **자유 문장과 사진**으로 muscle50을 쓴다.
  - "점심에 닭가슴살 한 팩이랑 햇반 먹었어" → 기록 제안 → 확인 → 저장
  - 음식 사진 → 무엇을 먹었는지 추정 → 기록 제안 → 확인 → 저장
  - "오늘 뭐 운동해?", "단백질 얼마 남았어?" → 기존 결과를 코치 말투로 짧게 답한다.
  - 구내식당 메뉴 화면 캡처 → 메뉴를 읽고, 오늘 남은 단백질·kcal에 맞는 메뉴를 추천 → "이걸로 먹을게" → 기록 제안
- LLM은 이 PC에 설치된 **공식 CLI를 사용자 본인 구독으로 실행**해서 쓴다. 제공자는 둘이고, 설정으로 고른다.
  - `claude`: Claude Code `claude -p`
  - `codex`: OpenAI Codex CLI `codex exec`
  - 사용자 결정(2026-10-12): 두 제공자를 모두 지원한다.
- 근거:
  - `docs/goals.md` 3절 "채팅으로 묻기"(v1·v1.1·v1.2 다음 단계로 예정된 자유 문장 v2).
  - 식사 기록 마찰을 줄여 측정 사이 리뷰와 조정 권고(우선순위 4·5)에 필요한 식단 기록을 쌓는다.
  - General Meal v1의 후속 후보: 사진·자유 문장 추정을 일반식에 붙인다.
  - 사용자 결정(2026-10-12): 구내식당(HD Life `grc.hd.com`) 메뉴는 **사용자가 보낸 캡처로만** 읽는다(안 A).
    회사 사이트 자동 로그인·자동 예약은 v2에 넣지 않는다(아래 Non-goals, 한계 참고).

## 범위 / Non-goals

- 범위:
  - 명령(`/`로 시작)이 아닌 텍스트와 사진 메시지를 LLM 계층이 처리한다. 기존 명령은 그대로 동작한다.
  - 처리하는 의도(intent)는 네 가지다.
    1. **식사 기록**(문장 또는 사진): LLM이 구조화된 제안을 만들고, bot이 검증한 뒤 사용자가 확인하면 기존
       `nutrition log` 경로로 저장한다.
    2. **질문**(운동, 영양, 회복, 체성분): bot이 기존 read 명령(`recommend --json`, `nutrition status --json`,
       `inbody trend --json` 등)을 실행하고, 그 JSON만을 근거로 LLM이 코치 말투로 짧게 답한다.
    3. **메뉴 캡처 추천**(사진): 구내식당 메뉴 화면 캡처를 받으면, LLM이 끼니(아침·점심·저녁)·코너·메뉴 이름과
       메뉴별 추정 영양값(범위)을 구조화해 돌려준다. bot이 오늘 `nutrition status --json`의 남은 단백질·kcal와 비교해
       정해진 규칙으로 추천 순서를 정한다. 사용자가 메뉴를 고르면 1번 식사 기록 제안(일반식+메모+추정값)으로 이어진다.
    4. **기타 잡담**: 페르소나로 짧게 답한다. 데이터를 지어내지 않는다.
  - 제공자 두 개(`claude`, `codex`)와, 설정 파일에서의 제공자·모델·페르소나·타임아웃 선택.
  - 대화 기억: chat마다 최근 대화 몇 개와 요약을 bot이 로컬 파일에 저장해 매 호출에 넣는다.
  - 대화 기록(history)과 보기 화면: 모든 자유 문장 대화를 로컬에 남기고, 지금 기억과 지난 기록을 Telegram과 PC에서
    볼 수 있다(사용자 요청 2026-10-12).
  - 페르소나: 이름, 말투, 성격을 설정에서 바꿀 수 있다. 기본값은 담백한 한국어 코치(존댓말).
- Non-goals:
  - **LLM이 직접 쓰지 않는다.** 모든 저장은 사용자의 확인을 거쳐 기존 CLI 명령으로만 한다. LLM에게 파일 쓰기,
    셸, 네트워크 도구를 주지 않는다.
  - **LLM이 판단하지 않는다.** 운동 추천, 영양 목표 판정, 숫자 계산은 지금처럼 muscle50 규칙이 한다.
    LLM은 받은 데이터를 말로 전달할 뿐이다.
  - API 키 제공자(Anthropic API, OpenAI API)는 v2에 넣지 않는다(후속 후보). 구독 토큰을 꺼내거나 중계하는 방식은
    쓰지 않는다.
  - 음성 메시지, 그룹 채팅, 먼저 말 걸기(예약 알림), 여러 사용자는 없다.
  - **회사 사이트(`grc.hd.com`)·HD Life 모바일 앱에 접속하지 않는다.** 로그인, 메뉴 자동 수집, 간편식(샐러드) 예약은
    없다. 회사 계정 ID/PW를 저장하지 않는다(`.env` 포함). 메뉴 캡처를 읽는 것만 한다.
  - 메뉴 추천은 `docs/goals.md` 우선순위 5의 메뉴 추천 기능이 아니다. 받은 메뉴 중 오늘 남은 양에 가까운 것을
    고르는 가벼운 도움이고, 조정 권고나 장기 식단 판단을 하지 않는다.
  - 기존 명령의 동작과 출력은 바뀌지 않는다. 기존 CLI 출력도 바뀌지 않는다.

## 명령 예시

설정(합성 예시, 파일 위치와 형식은 설계에서 정한다):

```json
{
  "provider": "claude",
  "claude": {"model": "sonnet"},
  "codex": {"model": null},
  "persona": {"name": "머슬", "tone": "존댓말, 짧게, 담백하게"},
  "timeout_seconds": 90,
  "fallback_provider": null
}
```

`model`이 `null`이면 그 CLI의 기본 모델을 쓴다(모델 옵션을 넘기지 않음). 사용자 결정(2026-10-12): 페르소나, 대체
제공자 끔, 모델은 위 기본값으로 한다.

Telegram(합성 값):

```text
사용자: 점심에 닭가슴살 한 팩이랑 햇반 먹었어
bot:   이렇게 기록할까요? (점심, 10-12)
       1. 닭가슴살 (chicken-breast) 1 pack
       2. 햇반 (hetbahn-white-210) 1 pack
       기록: /ok_7f3a   취소: /no_7f3a
사용자: /ok_7f3a
bot:   (기존 /log 답장과 같은 결과) … 취소: /void 2026-10-12-lunch-1
```

```text
사용자: (제육볶음 정식 사진) 저녁
bot:   이렇게 기록할까요? (저녁, 10-12, 사진 추정)
       1. 일반식 (메모: 제육볶음 정식, 사진 추정)
          추정: kcal 700~950, 단백질 30~45 g (estimated)
       기록: /ok_91c0   일반식만 기록(값 없이): /plain_91c0   취소: /no_91c0
```

```text
사용자: 오늘 뭐 운동해?
bot:   오늘은 하체예요. 스쿼트 40 kg 3×12부터 시작하세요. 어제 수면이 짧았으니 무게는 지난번과 같게 유지하세요.
       (근거: /today)
```

```text
사용자: (HD Life 식당 화면 캡처)
bot:   오늘 점심 메뉴예요. 남은 양: 단백질 62 g, kcal 1,150 (/status)
       추천 순서 (메뉴 값은 사진 추정, estimated)
       1. 한식: 제육볶음, 잡곡밥, 계란찜   단백질 35~50 g, kcal 750~950
       2. 간편식: 닭가슴살 샐러드        단백질 25~35 g, kcal 350~450
       3. 일품: 돈까스 카레              단백질 20~30 g, kcal 900~1,150
       먹을 메뉴: /eat_c2e1_1  /eat_c2e1_2  /eat_c2e1_3
사용자: /eat_c2e1_1
bot:   이렇게 기록할까요? (점심, 10-12, 메뉴 캡처 추정)
       1. 일반식 (메모: 한식 제육볶음 정식)
          추정: kcal 750~950, 단백질 35~50 g (estimated)
       기록: /ok_44d2   일반식만 기록(값 없이): /plain_44d2   취소: /no_44d2
```

제공자 바꾸기(합성 예시, 명령 이름은 설계에서 정한다):

```text
/llm            → 지금 제공자와 모델 표시
/llm codex      → codex로 전환
```

## 규칙

- 제공자 실행:
  - `claude`:
    - 수정하지 않은 공식 `claude` 실행 파일을 쓰고, 사용자 본인 구독 로그인을 쓴다.
    - `-p` 비대화형 실행, 결과 형식 고정(`--json-schema`), 세션 저장 안 함(`--no-session-persistence`).
    - 도구는 기본으로 모두 끈다(`--tools ""`).
    - 사용자 설정의 MCP 서버(예: claude.ai의 Gmail, Drive, Calendar, Notion 연결), hook, 메모리, CLAUDE.md, skill을
      불러오지 않는다. 설치된 2.1.290에서 확인한 후보: `--safe-mode`(로그인은 그대로 쓰고 사용자 설정을 끔),
      `--strict-mcp-config`(`--mcp-config` 없이 쓰면 MCP 서버 없음), `--setting-sources`. 어떤 조합을 쓸지는 설계에서
      정하고 실제로 꺼지는지 확인한다.
    - `--bare`는 쓰지 않는다(구독 로그인을 읽지 않음).
    - Claude Code에는 사진 옵션이 없다. 사진은 `--input-format stream-json`의 이미지 입력이나, 임시 폴더로 제한한
      읽기 도구로 넘긴다. 방법은 설계에서 정한다.
  - `codex`:
    - 수정하지 않은 공식 `codex` 실행 파일을 쓰고, 사용자 본인 로그인을 쓴다.
    - `codex exec` 비대화형 실행, 결과 형식 고정(`--output-schema`), 기록 안 남김(`--ephemeral`),
      읽기 전용 sandbox(`--sandbox read-only`), 사진은 `-i <파일>`로 붙인다.
    - Codex의 `-p`는 print가 아니라 `--profile`이다. 비대화형 실행은 `codex exec`다.
    - 사용자 설정(`~/.codex/config.toml`의 MCP 서버 등)과 execpolicy 규칙을 불러오지 않는다. 설치된 0.160.0에서 확인한
      후보: `--ignore-user-config`(로그인은 그대로 씀), `--ignore-rules`. 실제로 꺼지는지 설계에서 확인한다.
  - 둘 다 이 repo가 아닌 임시 작업 폴더에서 실행한다. 이 repo의 CLAUDE.md, AGENTS.md, hook이 끼어들지 않게 한다.
  - LLM이 할 수 있는 일은 "글을 읽고 JSON을 돌려주기"뿐이다. 메일 보내기, 파일 공유·삭제, 셸, 웹 접근 같은 도구가
    한 개도 없어야 한다.
  - 두 제공자 모두 문장과 사진을 처리한다. 고른 제공자가 사진을 처리하지 못하는 상태가 되면, 사진은 추정하지 않고
    "값 없이 일반식만 기록" 제안만 보낸다.
  - 정확한 옵션 이름과 동작은 설계 단계에서 설치된 버전의 `--help`로 확인한다.
  - 실행 시간 상한(timeout)을 둔다. 넘으면 그 제공자 실행을 중단하고 실패로 처리한다.
  - 실패하면(실행 파일 없음, 로그인 필요, 시간 초과, 형식 오류) 설정된 대체 제공자를 한 번 시도할 수 있다.
    대체 제공자는 기본으로 꺼져 있다(`null`). 켜면 메시지와 사진이 두 번째 회사로도 갈 수 있으므로 사용자가 직접 켠다.
    그래도 실패하면 "지금 해석하지 못했습니다. 명령어로 보내 주세요(/log …)"처럼 답하고 아무것도 쓰지 않는다.
- 식사 기록:
  - LLM 결과는 정해진 JSON 형식이어야 한다. 예: 끼니 종류, 날짜 표현, item 목록. item은 카탈로그 음식+수량+단위
    또는 일반식+메모(+추정값).
  - 날짜는 LLM이 계산하지 않는다. LLM은 "오늘", "어제" 같은 표현만 돌려주고, bot이 v1 D1 시간대 규칙으로 날짜를
    정한다. 기본은 오늘이다.
  - bot이 결과를 검증한다.
    - 카탈로그 음식은 Food Name Lookup v1 규칙(정확한 ID/이름/alias)으로만 연결한다. 연결되지 않으면 일반식+메모로
      바꾸어 제안한다. 비슷한 이름을 추측해 연결하지 않는다.
    - 단위가 그 음식에 없으면 제안에서 빼고, 이유를 보여 준다.
  - **저장 전에 반드시 사용자 확인을 받는다.** 확인 방식(탭하는 명령, inline 버튼 등)과 제안의 유효 시간은 설계에서 정한다.
    확인은 한 번만 쓰인다(중복 저장 없음, v1의 at-most-once 규칙).
  - 확인은 쓰기 명령이다. v1 D3대로, 적용되지 않은 migration이 있으면 저장을 거절한다. 또 v1 D2대로 오래된 메시지는
    처리하지 않는다.
  - 저장은 기존 CLI 경로(`nutrition log`, `--general`, `--additional` 등)를 그대로 쓴다. 답장은 기존 `/log` 답장과
    `취소: /void` 줄을 쓴다.
- 사진 추정:
  - 사진에서 추정한 영양값은 반드시 **추정(estimated)과 범위**로 다룬다. 정확한 값처럼 저장하거나 보여 주지 않는다.
  - 추정값을 일반식 item에 붙여 저장하는 방식은 설계에서 정한다(기존 snapshot·출처 구조, 예약된 `visual_estimate`
    출처). frontmatter의 `migration: none`은 템플릿 기본값이다. migration이 필요한지는 designer가 정하고, 필요하면
    번호는 orchestrator가 예약하고 운영 migration 게이트(gate 3)를 거친다.
  - 사용자는 "값 없이 일반식만 기록"을 언제든 고를 수 있다.
  - 추정값이 들어간 날은 기존 규칙대로 `estimated`로 표시된다. 추정값을 근거로 한 강한 판단(부족·초과 행동 안내)이
    나오는지 여부는 기존 영양 규칙을 따르고, 설계에서 확인한다.
  - 사진을 로컬에 보관할지(RAW 보존 원칙), 보관 기간은 설계에서 정한다. 사진은 선택한 제공자(Anthropic 또는 OpenAI)로
    전송된다는 점을 문서에 적는다.
- 메뉴 캡처 추천:
  - 캡처인지 음식 사진인지는 LLM이 구조화 결과의 종류로 알려 준다. 모호하면 bot이 "메뉴 캡처인가요, 먹은 음식
    사진인가요?"라고 묻고 추측하지 않는다.
  - 끼니는 사용자가 함께 적은 말(예: "점심")을 우선한다. 없으면 캡처에 보이는 끼니를 쓰고, 여러 끼니가 보이면
    D1 시간대 기준 현재 시각으로 다음 끼니를 고른다. 정확한 시각 경계는 설계에서 정한다.
  - 메뉴별 영양값은 LLM 추정이므로 언제나 범위와 `estimated`로 보여 준다. 메뉴판에 kcal 등이 적혀 있으면 그 값을
    쓰되 "메뉴판 표기"로 구분한다.
  - **추천 순서는 bot의 결정적 규칙이 정한다.** LLM은 메뉴를 읽고 값을 추정만 한다. 규칙(예: 남은 kcal 안에서 단백질
    추정 중간값이 큰 순서)은 설계에서 정하고 테스트로 고정한다. 같은 입력이면 같은 순서다.
  - 오늘 영양 목표나 남은 양을 알 수 없으면(목표 없음, 기록 불완전, 일반식이 있어 판정 불가 등) 순서를 매기지 않는다.
    메뉴 목록만 보여 주고 무엇이 없어서 추천하지 못하는지 말한다(추측 금지).
  - 추천 답의 숫자는 `nutrition status --json`의 값 또는 이번 캡처의 추정·표기 값만 쓴다. 숫자 검사에서 이 두 출처를
    함께 허용한다.
  - 메뉴를 고르는 것만으로는 저장하지 않는다. 고른 뒤 식사 기록 제안과 확인을 거친다.
  - 캡처에는 이름·사번 같은 개인정보가 보일 수 있고, 캡처는 고른 제공자로 전송된다. 문서에 "메뉴 부분만 잘라서
    보내기"를 권한다.
- 질문 답변:
  - 답의 모든 숫자는 bot이 넘긴 muscle50 JSON에서만 나와야 한다. 데이터에 없는 값은 "알 수 없음"이라고 말한다.
  - bot은 보내기 전에 답의 숫자를 검사한다. 넘긴 JSON에 없는 숫자가 있으면 LLM 답을 보내지 않고, 기존 명령 답장
    (`/today`, `/status` 등의 요약)을 대신 보낸다. 숫자를 비교하는 정확한 규칙(단위, 반올림)은 설계에서 정한다.
  - 답 끝에 근거 명령(예: `/today`, `/status`)을 붙여 사용자가 원본을 볼 수 있게 한다.
  - 의도를 판단하지 못하면 사용법(`/help`)을 안내한다. 명령을 추측해 실행하지 않는다.
- 대화 기억과 페르소나:
  - 기억은 로컬 상태 파일에 chat별로 저장한다. 최근 N개 대화와 짧은 요약만 남기고, 크기 상한을 둔다. DB에는 넣지 않는다.
  - `/forget` 같은 명령으로 기억을 지울 수 있다(명령 이름은 설계에서 정한다).
  - **기억 보기**: `/memory` 같은 명령으로 다음 호출에 LLM에게 넘어갈 기억(최근 대화, 요약)을 그대로 보여 준다.
- 대화 기록(history):
  - 기억과 따로, 자유 문장 대화를 빠짐없이 로컬 파일에 남긴다(append-only). 항목마다 시각(D1 시간대), chat,
    사용자 메시지(사진이면 "사진"과 저장 위치), 의도, 제공자·모델, bot 답장, 제안·확인·저장 결과(meal ID)를 적는다.
  - 기억의 크기 상한이나 `/forget`은 기록을 지우지 않는다. 기록은 사용자가 직접 지우기 전에는 보관한다. 위치는
    `%LOCALAPPDATA%\muscle50` 아래이며 DB 밖이다. 정확한 경로와 형식(예: 월별 JSONL)은 설계에서 정한다.
  - 보기: Telegram `/history [N | YYYY-MM-DD]`(최근 N개 또는 그날), PC `muscle50 telegram history ...`(읽기 전용).
    명령 이름과 출력 형식은 설계에서 정한다.
  - 콘솔 로그에 원문을 남기지 않는 v1 규칙은 그대로다. 기록 파일은 콘솔 로그가 아니다. 문서에 기록 파일의 위치와,
    그 안에 식단·대화 원문이 있다는 점을 적는다.
  - 페르소나는 말투만 바꾼다. 원칙(추측 금지, 데이터 밖 숫자 금지, 저장 전 확인)은 페르소나보다 우선한다.
- 보안과 개인정보:
  - 허용 목록에 있는 chat만 처리한다(v1 규칙).
  - 사용자 메시지와 LLM 답의 원문을 콘솔 로그에 남기지 않는다(v1 규칙). 실행한 제공자, 시간, 성공 여부만 남긴다.
  - Telegram 사진 다운로드 URL에는 bot token이 들어 있다. 이 URL은 로그, 오류 메시지, LLM 입력 어디에도 남기지 않는다.
  - 설정 파일에 비밀값을 두지 않는다. 각 CLI의 로그인은 그 CLI가 관리한다.
- 테스트:
  - 실제 `claude`·`codex`를 부르지 않는다. 제공자 실행을 가짜로 바꿔 넣는다(정해진 JSON, 시간 초과, 형식 오류,
    실행 파일 없음).
  - 실제 동작 확인은 통합 뒤 사용자가 한다.

## 인수 조건

- [ ] AC1: 가짜 제공자가 식사 JSON을 돌려주면, bot이 카탈로그 연결·검증한 제안을 보여 주고, 확인 명령을 받기 전에는
      DB가 변하지 않는다. 확인하면 같은 내용을 `nutrition log`로 기록한 것과 행이 같다.
- [ ] AC2: 카탈로그에 없는 음식, 없는 단위, 모호한 이름은 추측해 연결되지 않고 일반식+메모로 제안되거나 이유와 함께
      빠진다.
- [ ] AC3: 같은 확인 명령을 두 번 보내거나, 유효 시간이 지난 확인을 보내도 한 번만 저장되거나 아무것도 저장되지 않는다.
- [ ] AC4: 사진 추정 제안은 추정값을 범위와 `estimated`로 표시한다. "값 없이 일반식만 기록"을 고르면 영양값 없는
      일반식으로 저장된다.
- [ ] AC5: 가짜 제공자가 넘긴 JSON 안의 숫자만 쓴 답은 그대로 보내진다. 넘긴 JSON에 없는 숫자를 섞은 답은 보내지지
      않고, 같은 의도의 기존 명령 답장이 대신 보내진다.
- [ ] AC6: `provider`를 `claude`와 `codex`로 바꾸면 각각 정해진 CLI 인자로 실행된다(가짜 실행기로 argv 확인).
      대체 제공자가 꺼져 있으면(기본) 실패 시 다른 제공자를 부르지 않는다. 켜져 있으면 한 번 시도하고, 둘 다 실패하면
      명령어 안내와 함께 아무것도 쓰지 않는다. 사진 메시지는 두 제공자 모두에서 정해진 방식으로 사진을 넘긴다.
- [ ] AC7: 제공자 실행은 임시 작업 폴더에서, 도구 없이, 사용자 설정의 MCP 서버·hook·메모리를 불러오지 않는 옵션으로
      실행된다(argv와 작업 폴더 확인). 실제 CLI에서 꺼지는지는 설계 단계에서 한 번 확인하고 계획에 적는다.
- [ ] AC8: 기존 명령(`/today`, `/status`, `/log`, `/refresh` 등)과 기존 CLI 출력이 이 기능 전과 byte-identical이다.
      `/help`에 새 명령 줄이 추가되는 것은 예외다.
- [ ] AC9: 허용 목록 밖 chat의 사진·문장은 제공자를 부르지 않고 무시된다. 콘솔 로그에 메시지 원문과 사진 URL(bot
      token)이 없다.
- [ ] AC9a: 적용되지 않은 migration이 있으면 확인 명령이 저장을 거절한다. "어제 저녁" 같은 날짜 표현은 bot이 D1
      시간대 규칙으로 정한 날짜로 저장된다.
- [ ] AC9b: 가짜 제공자가 메뉴 캡처 결과(끼니, 메뉴, 추정 범위)를 돌려주면, 같은 영양 상태에서 추천 순서가 항상 같고
      설계에서 정한 규칙과 일치한다. 남은 양을 알 수 없는 날은 순서 없이 메뉴 목록과 이유만 보낸다.
- [ ] AC9c: 메뉴를 골라도 확인 전에는 DB가 변하지 않는다. 확인하면 메모와 추정값이 있는 일반식으로 저장되고,
      "값 없이 일반식만 기록"도 고를 수 있다.
- [ ] AC9e: 자유 문장 대화 한 번마다 기록 파일에 한 항목이 추가된다. `/forget` 뒤에도 기록은 남고, `/memory`는 비어 있다.
      `/history`와 `muscle50 telegram history`가 같은 항목을 보여 준다.
- [ ] AC9d: 이 기능은 `grc.hd.com` 등 외부 사이트에 접속하지 않는다(네트워크 호출은 Telegram API와 제공자 CLI뿐).
- [ ] AC10: 품질 게이트 4개가 통과한다.

## 한계 / 후속 후보

- 응답이 몇 초~수십 초 걸린다(CLI를 매번 새로 실행). PC가 켜져 있고 `telegram run`이 실행 중일 때만 동작한다.
- 구독 사용량을 쓴다. Claude Code·Codex를 코딩에 쓰는 한도와 나눠 쓴다.
- 구독을 개인 자동화에 쓰는 것이 각 회사 약관의 "일반적인 개인 사용"에 들어가는지는 명확하지 않다(회색지대). 사용자가
  이 점을 알고 쓴다.
- 사진 칼로리 추정은 오차가 크다(흔히 ±30~50%). 추정값은 참고용이다.
- 메뉴 캡처 추천은 사용자가 캡처를 보내야 동작한다. 캡처를 읽는 정확도는 화면 글씨 크기와 잘림에 따라 다르다.
- 후속 후보: API 키 제공자, 음성 메시지, 아침 자동 요약, "일반식 N끼"·추정 비율 통계, 자주 먹는 메뉴 학습.
- 후속 후보 `cafeteria-auto`(v3 이후): HD Life 메뉴 자동 수집(안 B)과 간편식(샐러드) 예약(안 C, 매번 Telegram 확인).
  - 조건: **회사 IT·보안 담당의 자동 접속 허용을 먼저 받는다.** "HD현대 계열사" 로그인은 그룹 SSO
    (`saml.hhigroup.site`)를 거치고, 같은 계정이 사내 메일·그룹웨어에도 쓰일 가능성이 높다. 로그인 5회 실패 시 잠김,
    30분 세션 만료가 있다(2026-10-12 로그인 페이지 확인).
  - 허용되면 비밀번호는 `.env`가 아니라 Windows 자격 증명 관리자 등 OS 보관소에 둔다. 모바일 앱 트래픽 분석은 하지 않는다.
