# Telegram LLM Corrections and Range Totals v2.3

## 목적

- 자유 문장으로 **방금 기록한 식사를 고칠 수 있게** 하고, 라벨 값과 오늘 누적 표시를 실제 사용에 맞게 고친다.
- 근거: 2026-10-14 아침 실사용(`muscle50 telegram history`).
  - 삼각김밥 영양정보 라벨 사진에서 읽은 단백질 5 g이 "범위가 아니라 한 값"이라는 재확인 규칙에 걸려 다시 묻고,
    "(값 확인 필요)"가 붙었다. 인쇄된 라벨 값은 원래 한 값이다.
  - 바로 뒤 "삼각김밥 지방 2g 이네 사진에 나와있어"가 고치기가 아니라 **새 아침 식사**(`--additional`)로 제안·기록되어
    아침이 두 번 기록됐다(사용자 요청으로 `2026-10-14-breakfast-1`을 void했다).
  - "아니 아침 1식을 수정해야지 하나 더 추가하면 어떻게해"는 식사 수정 의도였지만 대상을 찾지 못했다(일반식 item은
    카탈로그 이름이 없어 찾을 수 없음, "아침 1식"을 이해하지 못함, 일반식 추정값 수정 기능 없음).
  - 오늘 누적의 "확인 240 + 추정 360~380" 표시는 읽기 어렵다. 사용자 결정(2026-10-14): **늘 하나의 범위**로 보여 준다.
- `docs/goals.md` 3절 하루 흐름 2(먹은 것 기록 → 남은 양 확인)의 기록 정확도를 높인다.

## 범위 / Non-goals

- 범위:
  1. **라벨 값**: 사진이나 사용자가 알려 준 라벨(영양정보 표시)에서 읽은 값은 한 값(min = max)으로 둘 수 있다. 이런
     값은 "범위가 아니라 한 값" 재확인 대상이 아니다. 다른 재확인(열량과 탄단지 합 등)은 그대로 한다.
  2. **이어지는 고치기**: 같은 chat에서 방금 기록했거나 제안한 식사에 대한 말("지방 2g이네", "아니 2팩 아니고 1팩",
     "그거 점심이야")은 그 식사를 고치는 제안으로 다룬다. 새 식사로 기록하지 않는다.
  3. **같은 끼니가 이미 있을 때**: 오늘 같은 끼니가 이미 있고 새 item이 기존 item과 겹치면(같은 카탈로그 음식, 또는 같은
     일반식 메모), 하나 더 기록하지 않고 "기존 아침을 고칠까요, 하나 더 기록할까요?"를 묻는다. 겹치지 않으면 v2처럼
     `--additional`로 하나 더 기록하되 그 사실을 제안 맨 위에 눈에 띄게 적는다.
  4. **식사 수정 대상 찾기 확장**:
     - 일반식 item은 메모로 찾는다(정확 일치 또는 메모에 포함된 말, 여러 개면 후보를 보여 주고 추측하지 않음).
     - "아침 1식", "아침 첫 번째", "방금 기록한 거", "방금 거"를 그날 그 끼니의 순서나 이 chat의 마지막 기록 식사로
       결정적으로 해석한다.
     - 일반식 item의 추정값(범위)과 메모를 바꿀 수 있다(필요하면 기존 meal 수정 명령에 추정값 옵션을 더한다).
  5. **오늘 누적을 하나의 범위로**: 확인 값과 추정 범위를 더해 `kcal 600~620`처럼 보여 준다. 추정이 없으면 한 숫자다.
     값을 모르는 item은 0으로 더하지 않고 "값 모르는 항목 N개 빠짐"으로 적는다. 머리에 "(추정 포함)"을 붙인다.
- Non-goals:
  - 범위를 근거로 한 판단(부족·초과 안내)은 하지 않는다. 사용자 결정(2026-10-14): 범위 값만 보여 준다. 추정이 있는 날의
    status·추천 판단은 지금과 같다.
  - 확인 없이 고치지 않는다. 모든 수정은 제안 → `/ok` 뒤에만 실행한다.
  - 기존 CLI 텍스트·JSON 출력(`nutrition day`, `status` 등)은 바꾸지 않는다. 바뀌는 것은 Telegram LLM 답장의 누적 줄과
    새 수정 흐름이다. meal 수정 명령에 새 옵션이 생기면 그 `--help`와 그 옵션을 쓴 출력만 더해진다.
  - migration 없음.

## 명령 예시

Telegram(합성 값, 정확한 문구는 설계에서 정한다):

```text
사용자: (삼각김밥 라벨 사진) 아침으로 삼각김밥이랑 닭가슴살 먹음
bot:   이렇게 기록할까요? (아침, 10-14, 사진 추정)
       1. 일반식 (메모: 깻잎닭갈비 삼각김밥 1개)
          라벨: kcal 185, 단백질 5 g, 탄수화물 37 g
       2. 닭가슴살 (chicken-breast) 1 pack (수량 추정)
       기록: /ok_c229 ...
사용자: /ok_c229
bot:   (기존 /log 답장) … 취소: /void 2026-10-14-breakfast-1
       오늘 누적 (추정 포함): kcal 305, 단백질 23 g, 탄수화물 39 g, 지방 4 g (값 모르는 항목 1개 빠짐)
사용자: 삼각김밥 지방 2g 이네 사진에 나와있어
bot:   방금 기록한 아침(2026-10-14-breakfast-1)을 이렇게 고칠까요?
       item 1 깻잎닭갈비 삼각김밥 1개: 지방 알 수 없음 → 2 g
       고치기: /ok_7a4a   취소: /no_7a4a
```

```text
사용자: 아침 1식 닭가슴살 2팩으로 바꿔줘
bot:   아침(2026-10-14-breakfast-1)을 이렇게 고칠까요?
       item 2 닭가슴살: 1 pack → 2 pack
       고치기: /ok_91c0   취소: /no_91c0
```

```text
사용자: 아침에 삼각김밥 먹었어   (오늘 아침에 이미 삼각김밥이 있음)
bot:   오늘 아침(2026-10-14-breakfast-1)에 이미 삼각김밥이 있습니다.
       기존 아침 고치기: /fix_3b1e   하나 더 기록: /ok_3b1e   취소: /no_3b1e
```

## 규칙

- 라벨 값:
  - LLM 결과의 item에 "라벨에서 읽음" 표시를 둔다(사진 속 영양정보 표시, 또는 사용자가 문장으로 알려 준 라벨 값).
    표시가 있는 값은 min = max여도 된다. 라벨에 없는 영양소는 모름(null)이다.
  - 저장 출처 구분(예: 추정 출처에 라벨 표시)과 제안 화면 문구("라벨:")는 설계에서 정한다. migration 없이 기존 출처 값과
    출처 문구로 표현한다.
  - "범위가 아니라 한 값" 검사만 건너뛴다. 열량과 탄단지 합 검사, 범위 폭 검사, 가정 숫자 검사는 그대로다.
- 이어지는 고치기:
  - bot은 chat별로 마지막으로 기록한 식사 ID(이번 bot 실행과 상관없이 history나 상태 파일에서)와 아직 열린 제안을 안다.
    LLM에게 "직전 기록 식사"의 item 목록(번호, 이름 또는 메모, 수량, 값)을 넘긴다.
  - LLM이 "직전 기록을 고침"으로 해석하면, bot이 그 식사와 item을 결정적으로 확인해 수정 제안을 만든다. 대상이 하나로
    정해지지 않으면 후보를 보여 주고 추측하지 않는다.
  - 직전 기록이 오래됐으면(시간 기준은 설계에서 정한다) "직전 기록"으로 보지 않는다.
  - 아직 확인 전인 제안을 고치는 말이면, 그 제안을 고친 새 제안을 보여 주고 이전 제안은 취소 상태로 둔다.
- 같은 끼니 겹침:
  - 겹침 판단은 결정적이다: 같은 날 같은 끼니에 같은 카탈로그 food ID, 또는 같은 일반식 메모(정규화 후 일치)가 있으면 겹침.
  - 겹치면 고치기 / 하나 더 기록 / 취소를 고르게 한다. 고치기를 고르면 수정 제안으로 이어진다(확인 필요).
- 식사 수정 대상:
  - "아침 1식" = 그날 아침 중 기록 순서 1번째(void 제외). "방금 기록한 거" = 이 chat의 마지막 기록 식사.
  - 일반식 item은 메모로 찾는다. 카탈로그 item은 지금처럼 정확 일치로 찾는다. 모호하면 후보만 보여 준다.
  - 일반식 추정값·메모 수정은 기존 meal 수정 명령으로 한다. 명령에 추정값 옵션이 없으면 더한다(`--general-estimate`와
    같은 형식). 수정 이력은 append-only 원칙을 따른다(기존 수정 명령 방식 그대로).
- 오늘 누적 범위:
  - 영양소마다: 하한 = 확인 값 합 + 추정 하한 합, 상한 = 확인 값 합 + 추정 상한 합. 하한 = 상한이면 한 숫자로 쓴다.
  - 값 모르는 item은 더하지 않고 개수만 적는다. 오늘 기록이 없으면 "오늘 기록 없음 (0이 아님)" 그대로다.
  - 이 표시는 Telegram LLM 답장(`/ok` 뒤, 질문 답변 데이터, 메뉴 머리)에만 쓴다. CLI 출력은 그대로다.
  - LLM에게 넘기는 데이터의 누적도 같은 범위 형식으로 바꾸고, 숫자 검사는 그 숫자를 허용한다.

## 인수 조건

- [ ] AC1: 라벨 표시가 있는 한 값(min = max)은 "범위가 아니라 한 값" 재확인을 일으키지 않고 "(값 확인 필요)"가 붙지 않는다.
      라벨 표시가 없는 한 값은 지금처럼 재확인한다.
- [ ] AC2: 식사를 기록한 직후 "지방 2g이네" 같은 말은 그 식사를 고치는 제안이 되고, `/ok` 뒤 그 식사가 고쳐진다. 새 식사가
      생기지 않는다. 확인 전에는 DB가 바뀌지 않는다.
- [ ] AC3: 같은 날 같은 끼니에 겹치는 item이 있으면 고치기 / 하나 더 / 취소를 묻고, 겹치지 않으면 하나 더 기록한다는 말을
      제안 맨 위에 보여 준다.
- [ ] AC4: "아침 1식", "방금 기록한 거"가 결정적으로 해석되고, 일반식 item을 메모로 찾으며, 모호하면 후보만 보여 주고 아무것도
      쓰지 않는다.
- [ ] AC5: 일반식 item의 추정 범위와 메모를 고칠 수 있다. 고친 뒤 `nutrition day`에 새 값이 반영되고 이전 값은 수정 이력으로
      남는다.
- [ ] AC6: 오늘 누적이 영양소마다 하나의 범위(또는 한 숫자)로 나오고, 모르는 값은 0으로 더하지 않고 개수로 적힌다.
- [ ] AC7: 확인 전 제안을 고치는 말은 고친 새 제안을 만들고 이전 제안은 더 이상 `/ok`로 실행되지 않는다.
- [ ] AC8: 기존 CLI 출력, LLM이 꺼져 있을 때의 bot, 입력한 명령(`/log`, `/void` 등)의 답장은 byte-identical이다. meal 수정
      명령에 새 옵션이 생기면 그 `--help`와 그 옵션을 쓴 출력만 다르다.
- [ ] AC9: 품질 게이트 4개가 통과한다.

## 한계 / 후속 후보

- "직전 기록"이 무엇인지는 시간과 chat 기준의 결정적 규칙이다. 여러 식사를 한 번에 고치는 말은 후보를 보여 준다.
- 범위 기반 판단(부족·초과 안내)은 후속 후보다.
- 후속 후보: 수정 이력을 Telegram에서 보기, 자주 쓰는 일반식을 카탈로그로 승격.
