# Telegram LLM Failure Replies and Meal Merging v2.5

## 목적

- LLM 호출이 실패하면 **이유와 할 일**을 알려 주고, 같은 메시지를 한 번 눌러 다시 보낼 수 있게 한다.
- "기존 아침에 같이 기록해줘"처럼 이미 있는 끼니에 더하는 말을 이해한다.
- 열린 제안을 고치는 말을 한 번에 반영하고, 코치가 bot 명령과 동기화 상태를 알고 답한다.
- 근거(v2.4 통합 뒤 2026-10-16~20 실사용, `muscle50 telegram history`):
  1. 10-16 23:27~23:30에 글 3개가 모두 `claude/haiku failed`("지금 해석하지 못했습니다")였고, 사진 1장도 같은 시각에
     "사진을 받지 못했습니다"였다. 그날 아침·점심·저녁이 기록되지 않아 10-21에 손으로 다시 기록했다. 사진 다운로드도 같이
     실패했으므로 사용 한도보다 네트워크 문제였을 가능성이 크지만, 지금 답장으로는 구분할 수 없다.
  2. "아침은 하나에 같이 기록해줘"라고 했는데 바나나만 있던 `breakfast-1`에 더하지 않고 `breakfast-2`를 만들었다.
  3. 열린 제안에 "멕시코 타코도 반개"를 두 번 말해야 반영됐다(Haiku가 앞선 수정을 놓침).
  4. "동기화 명령어 뭐야?"에 코치가 "명령어 목록을 확인할 수 없다"고 답했다.
  5. 10-09~10-18이 동기화되지 않았는데 코치는 "마지막 운동 10-07", "회복 기록 없음"이라고만 답했다.
- `docs/goals.md` 3절 "채팅으로 묻기"를 매일 믿고 쓸 수 있게 한다.

## 범위 / Non-goals

- 범위:
  1. **실패 이유 분류**: 호출 결과를 `network`(연결 실패), `usage_limit`(사용 한도), `login`(로그인 필요), `timeout`,
     `not_found`(실행 파일 없음), `other`로 나눈다. 판단은 종료 코드와 CLI가 낸 짧은 오류 표시(예: Claude `result` 이벤트의
     `is_error`·문구, stderr의 알려진 표시)만으로 결정적으로 한다. 원문은 저장·출력하지 않는다. history에 이유를 남긴다(additive).
  2. **실패 답장**: 이유별 한 문장 + 할 일. 예: 사용 한도 → "Claude 사용 한도에 걸렸습니다. 잠시 뒤 다시 보내거나 `/llm codex`로
     바꾸세요." 네트워크 → "인터넷 연결이 끊긴 것 같습니다." 그리고 누를 수 있는 `/retry_<짧은 id>`(60분 유효)를 붙인다.
     사진도 다운로드가 실패하면 같은 방식으로 `/retry_`를 붙인다(사진 file id를 다시 받는다).
  3. **`/retry_<id>`**: 실패한 메시지 하나를 처음 받은 것처럼 다시 처리한다. 한 번만 쓰인다. 실패 메시지 원문은 상태 파일에만
     60분 보관하고 그 뒤 지운다.
  4. **사용 한도 때 다른 제공자로**: `usage_limit`일 때만 다른 제공자(Codex)로 한 번 넘기는 설정 `fallback_on_usage_limit`를 더한다.
     기본값은 설계 승인 때 사용자가 정한다(추천: 켜짐, 다른 실패는 지금처럼 `fallback` 설정을 따름).
  5. **기존 끼니에 더하기**: 식사 기록 제안에서 "같이", "하나에", "기존 ~에 추가", "~에 더해" 같은 말이 있고 같은 날 같은 끼니가
     이미 있으면, 새 끼니(`--additional`) 대신 그 끼니에 item을 더하는 제안(기존 `add_item` 수정)을 만든다. 여러 끼니 제안
     안에서도 끼니마다 고를 수 있다. 제안에 "기존 아침(2026-10-16-breakfast-1)에 추가"처럼 보여 준다.
     말이 없는데 같은 끼니가 이미 있으면 지금처럼 새 끼니를 제안하되, 기존 끼니에 더하는 명령을 같이 보여 준다(설계에서 확정).
  6. **열린 제안 고치기**: 열린 제안을 고치는 호출은 `retry_model`(Claude 기본 sonnet)을 쓴다. 프롬프트에 지금 제안 전체와
     이번 대화의 앞선 수정 요청을 함께 넣는다. 결과가 앞선 수정(양, 추가, 삭제)을 되돌리면 형식 실패로 보고 한 번 다시 시도한다
     (설계에서 비교 규칙을 정한다).
  7. **코치가 bot 명령을 앎**: 질문 답변 프롬프트에 `help_text(llm_enabled=True)`의 명령 목록을 넣는다. "명령어 뭐야?" 같은 질문에는
     누를 수 있는 명령으로 답한다.
  8. **동기화 상태를 앎**: 질문 답변 프롬프트에 최근 14일 coverage 요약(동기화 안 된 날짜 구간)을 넣는다. 운동·회복 질문에서
     빠진 날이 있으면 "10-09~10-18은 동기화되지 않았습니다"와 `/daily`(또는 `daily-catch-up`이 있으면 `/sync`)를 안내한다.
     "기록 없음"과 "동기화 안 됨"을 구분해 말한다.
- Non-goals:
  - LLM이 동기화나 기록을 직접 실행하지 않는다(제안과 안내만).
  - 새 Garmin 호출 없음. coverage는 읽기만 한다.
  - LLM이 꺼진 bot과 CLI 출력은 바꾸지 않는다. migration 없음.

## 명령 예시

Telegram(합성 값, 정확한 문구는 설계에서 정한다):

```text
사용자: 오늘 아침 밥한공기 굴비 작은거 두마리 미역국 건더기만 먹었어
bot:   인터넷 연결이 끊긴 것 같아 해석하지 못했습니다. 연결되면 눌러 다시 보내세요(60분 유효):
       /retry_3f2a
```

```text
사용자: 아침에 고구마도 먹었어 아침은 하나에 같이 기록해줘
bot:   기존 아침 2026-10-16-breakfast-1(바나나 1개)에 추가합니다:
       + 일반식 (메모: 고구마 1개, 약 150g 가정) kcal 180~220 · 단백질 2~3 g
       기록: /ok_9b1e   새 아침으로 따로: /new_9b1e   고치기: 그냥 말하세요
```

```text
사용자: 동기화 명령어 뭐야?
bot:   운동·회복 받아오기는 /daily 입니다. 운동 하나만 다시 받으려면 /refresh 를 쓰세요.
       /daily
       /refresh
```

`muscle50 telegram history`(합성):

```text
2026-10-16 23:27 +09:00 chat 111 text claude/haiku failed reason=network web=0
```

## 규칙

- 실패 이유는 고정 목록이다. 모르는 실패는 `other`이고 지금 문구("지금 해석하지 못했습니다 …")에 `/retry_`만 더한다.
- `/retry_`로 다시 처리한 메시지도 허용 목록, 오래된 메시지, 큰 사진 규칙을 그대로 따른다. 재시도로 같은 끼니가 두 번
  기록되지 않는다(제안 단계를 거치므로 `/ok` 전에는 아무것도 쓰지 않는다).
- 기존 끼니에 더하는 제안은 `/ok` 때 그 끼니가 아직 있고 void되지 않았는지 다시 확인한다. 없으면 `오류:`이고 아무것도 쓰지 않는다.
- 프롬프트에 넣는 명령 목록과 coverage 요약에는 token, chat id, 계정 정보가 없다.
- 숫자 반올림, 범위, "모르는 값은 0이 아님" 규칙은 v2.3·v2.4 그대로다.

## 인수 조건

- [ ] AC1: 가짜 실행기로 네트워크 오류, 사용 한도, 로그인 필요, 시간 초과, 실행 파일 없음을 만들면 각 이유가 history와
      답장에 맞게 나오고 원문은 어디에도 남지 않는다.
- [ ] AC2: 실패 답장에 `/retry_<id>`가 있고, 누르면 같은 메시지가 한 번 다시 처리된다. 만료(60분), 재사용, 다른 chat은 거부된다.
      60분 뒤 상태 파일에 원문이 없다.
- [ ] AC3: `fallback_on_usage_limit`가 켜져 있으면 사용 한도일 때만 Codex로 한 번 넘기고, 꺼져 있으면 넘기지 않는다.
- [ ] AC4: "하나에 같이 기록해줘" + 같은 날 같은 끼니가 있으면 `add_item` 제안이 되고, `/ok` 뒤 기존 끼니 ID가 그대로이며 item이 늘어난다.
      `/new_`는 새 끼니를 만든다. 여러 끼니 제안에서도 끼니별로 동작한다.
- [ ] AC5: 열린 제안 고치기 호출은 `retry_model`로 실행되고, 두 번째 수정에서 첫 번째 수정이 유지된다.
- [ ] AC6: 질문 답변 프롬프트에 명령 목록과 최근 14일 coverage 요약이 있고, 빠진 날이 없으면 coverage 줄은 "빠진 날 없음"이다.
- [ ] AC7: LLM이 꺼진 bot과 기존 CLI 출력은 byte-identical이다.
- [ ] AC8: 품질 게이트 4개가 통과한다.

## 설계 승인 결정 (2026-10-21)

- **기본 제공자는 Codex**다(처음에는 "코드 기본값은 claude 그대로"(P1)로 승인했다가, 같은 날 사용자 결정 "그냥 클로드가 하던 모든일을
  코덱스로 바꿔"로 P2). `{}` 설정이면 모든 호출이 Codex로 가고, Claude는 사용 한도 대체와 `/llm claude`로 남는다. `"provider": "claude"`를 적은
  설정은 v2.4처럼 동작한다(이번에 바뀐 답장·프롬프트 규칙은 제외).
- **Codex 모델은 Sonnet급 `gpt-6.1-sol`**(글·사진), 재시도 모델 없음(사용자 결정). Claude 모델 기본값(haiku/sonnet/sonnet)은 그대로다.
- `fallback_on_usage_limit`의 기본값은 **켜짐**이고, 다른 제공자가 답하면 답장에 한 줄로 알린다(D2).
- **웹 검색은 Claude로만**(D3). 처음 결정(W3: Codex에서도 검색)은 Codex가 격리 argv의 `--disable code_mode_host` 아래서 검색하지 못해
  만들 수 없었다. 사용자 결정 "검색만 클로드해"로 Codex 격리는 main 그대로 두고, 해석 item의 `lookup_wanted`가 true인 식사 기록만 Claude가
  웹 검색으로 한 번 다시 읽어 그 답으로 바꾼다. 새 설정 key는 없다(`web_search`를 그대로 쓴다).
- 열린 제안이 있는 동안의 글은 `retry_model`로 처음부터 돈다(D4 E1). 기존 끼니 더하기 말이 없어도 같은 끼니가 하나면 `/add_`를 붙인다(D6 J-B).
  한 기능, 커밋 두 묶음(D7).
- **범위 6의 "앞선 수정을 되돌리면 한 번 더" 검사는 하지 않는다**(D5 R0, 사용자 승인). spec에서 벗어난 부분이고 `docs/telegram-llm.md`에 적었다.
- Codex가 `~/.codex/AGENTS.md`를 읽는 남는 위험(2026-10-13에 "기본은 claude"를 근거로 받아들임)이 이제 모든 메시지에 해당한다. 사용자가
  2026-10-21에 받아들였다.

## 한계 / 후속 후보

- 실패 이유는 CLI가 내는 표시에 기대므로 CLI가 문구를 바꾸면 `other`로 떨어질 수 있다.
- "같이", "하나에" 판단은 LLM이 하므로 놓칠 수 있다. 그래서 제안에 `/new_`와 기존 끼니 표시를 같이 둔다.
- 후속 후보: **Codex 검색만 켜는 옵션(코드 모드 없이)이 생기면 Codex 검색으로 바꾸기**, 작업별 사용량 통계, v3 agent 모드(읽기 도구 +
  제안만 하는 쓰기 도구).
- 구현자·검증자가 보고한 한계:
  - 실패 이유 표식은 CLI 문구에 기댄다. 사용 한도 문구는 live로 만들 수 없어 알려진 문구로만 맞췄다(live 확인 안 됨). `rate limit`·`quota` 같은
    넓은 낱말은 다른 뜻의 오류를 잘못 분류할 수 있다(답장 문구만 달라진다). Claude 네트워크 끊김은 CLI가 스스로 다시 시도하므로 시간 초과까지 기다린다.
  - Claude 검색 여부는 Codex가 채운 `lookup_wanted`가 정한다. live 확인은 합성 문장 두 개뿐이라 누락률은 모른다. 검색하는 메시지는 호출이 둘이라
    더 늦고(Codex 약 12~17 s 뒤 Claude 최대 150 s) Claude 사용량도 쓰며, 메시지와 사진이 OpenAI와 Anthropic 둘 다로 간다.
  - Codex가 사용 한도에 걸려 Claude가 대신 답하면 검색 없이 답한다(상표 음식도 `출처` 없음). 반대로 `"provider": "claude"`에서 Claude가 막혀
    Codex가 답하면 Claude 검색을 건너뛴다.
  - 열린 제안 고치기를 `retry_model`로 돌리는 규칙(E1)은 Codex에서는 효과가 없다(재시도 모델이 없어 같은 `gpt-6.1-sol`). Claude에서는 제안이
    열린 60분 동안 관계없는 글도 Sonnet으로 돌아 사용량이 는다.
  - 만료된 다시 보내기 원문은 bot이 도는 동안(시작 때와 쉬는 poll마다)만 지운다. bot이 꺼져 있으면 다음 시작 때 지운다.
  - 앞선 수정을 되돌렸는지 보는 검사(D5)는 빠졌다(R0, 사용자 승인). 모델과 요청 사슬로 원인을 줄이고, 고친 제안 전체가 `/ok` 전에 보인다.
  - Codex의 `~/.codex/AGENTS.md` 위험이 모든 메시지에 해당한다(2026-10-21 받아들임). 사용 한도 대체는 따로 묻지 않고 두 번째 회사로 보낸다(기본 켜짐).
  - `gpt-6.1-sol` 같은 모델 이름은 바뀐다. 없어지면 `telegram_llm.json`의 `codex.model`/`photo_model`로 바꾼다.
  - 동기화 상태는 coverage 기록에 기대므로 `garmin latest`·`garmin refresh`만 쓴 날은 `동기화 안 됨`으로 보인다.
  - 아직 하지 않은 수동 확인(필수 게이트 아님): 실제 메시지로 Telegram에서 Claude 검색 확인. migration과 Garmin 변경은 없다.
